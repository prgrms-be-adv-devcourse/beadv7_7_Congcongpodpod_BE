# PR 컨벤션

본 저장소의 Pull Request 작성 가이드입니다. PR 생성 시 아래 규칙과 양식을 따릅니다.

## 브랜치 흐름

```text
feature | fix | refactor → develop → main
hotfix → main
```

- 일반 작업 브랜치는 `develop` 최신에서 분기합니다.
- 일반 PR은 `develop`을 대상(base)으로 만듭니다. `feature → main` PR은 금지입니다.

## PR 제목

```text
[TYPE] 한글 설명
```

제목은 변경 내용을 요약하며, `[TYPE]`은 아래 표기를 따릅니다.

| TYPE | 의미 |
|---|---|
| `[Feature]` | 새로운 기능 |
| `[Fix]` | 일반 버그 수정 |
| `[Hotfix]` | 운영 긴급 수정 |
| `[Refactor]` | 기능 변경 없는 구조 개선 |
| `[Docs]` | 문서 작성·수정 |
| `[Test]` | 테스트 작성·개선 |
| `[Deploy]` | 배포·운영 작업 |

## PR 본문 양식

아래 템플릿을 사용합니다.

```markdown
## 📌 작업 내용 (Summary)
- 무엇을 했는지 요약

## 🔗 관련 이슈 (Related Issue)
- Closes #이슈번호      (이슈를 완전히 해결하는 경우)
- 관련 이슈: #이슈번호   (부분 작업·관련만 있는 경우)

## 💡 변경 사항 (Changes)
- [ ] 기능 추가
- [ ] 버그 수정
- [ ] 디자인 변경
- [ ] 코드 리팩토링
- [ ] 문서 작성/수정

### 세부 변경 내역
- 구체적인 변경 내용

## 📸 스크린샷 (선택)
- UI 변경이 있을 때 첨부 (없으면 "해당 없음")

## 🧪 테스트 결과 (Test Results)
- **테스트 방법:** ...
- **테스트 결과:** ...

## ⚠️ 리뷰 시 참고 사항 (Notes for Reviewer)
- 리뷰어가 확인했으면 하는 부분
```

## 작성 규칙

1. 이슈를 완전히 해결하면 `Closes #번호`, 일부만 반영하면 `관련 이슈: #번호`로 링크합니다.
2. `## 💡 변경 사항`의 체크박스는 실제 변경에 해당하는 항목만 체크합니다.
3. 변경 이유(왜)와 내용(무엇)을 함께 서술합니다.
4. 실행한 테스트와 결과를 구체적으로 남깁니다.
5. Config·DB·API·배포에 영향이 있으면 영향 범위를 명시합니다.
6. 반드시 리뷰어를 1명 이상 지정합니다.
7. CI가 실패한 상태로 머지하지 않습니다.
8. 최종 리뷰 요청 전에 최신 `develop`을 머지해 충돌을 해결합니다.

## 커밋 메시지

```text
Type: 한글 제목

- 무엇을 변경했는지
- 왜 변경했는지
```

- Type은 `Feat`, `Fix`, `Docs`, `Refactor`, `Test`, `Chore`, `Design`, `Rename`, `Remove`, `Comment` 등을 사용합니다.
- 제목과 본문은 한글로 작성하고, 소문자 형태(`feat:` 등)는 사용하지 않습니다.
